# Observability

What the inference endpoint exposes, where it goes and what is deliberately
left out. The monitoring stack itself (Prometheus, Grafana, Loki, Alloy) is
platform-lab's ([its docs/observability.md](https://github.com/JGGHalfhide/platform-lab/blob/main/docs/observability.md)).

## Metrics

llama-server runs with `--metrics`; a ServiceMonitor
(`deploy/llm/servicemonitor.yaml`) has Prometheus scrape `/metrics` on the
Service every 15 s. The NetworkPolicy admits Prometheus on 8080.

| Metric | Type | Meaning |
|---|---|---|
| `llamacpp:prompt_tokens_total`, `llamacpp:prompt_seconds_total` | counter | Prompt tokens processed (not from cache) and the time spent on them |
| `llamacpp:prompt_tokens_cached_total` | counter | Prompt tokens reused from the KV cache |
| `llamacpp:tokens_predicted_total`, `llamacpp:tokens_predicted_seconds_total` | counter | Generated tokens and the time spent generating |
| `llamacpp:requests_processing`, `llamacpp:requests_deferred` | gauge | Requests in a slot; requests waiting for one |
| `llamacpp:n_busy_slots_per_decode` | gauge | Average slots batched per decode call |
| `llamacpp:n_tokens_max` | counter | Longest sequence seen (prompt + generation) |

llama-server exports **no latency histograms**: time to first token and
p50/p95 latency are measured client side (`scripts/cold-start.sh` now, the
Week 6 load test later), not in Prometheus. When KEDA has scaled the server
to zero there is no target and the `llamacpp:*` series stop; the dashboard
shows 0 ready replicas instead.

Container memory, CPU, replicas and restarts come from the platform's
cAdvisor and kube-state-metrics.

## Dashboard

`deploy/monitoring/dashboards/llama-server.json`, generated by
`scripts/gen-dashboard.py` (`make dashboard`; edit the script, not the
JSON). Kustomize turns it into a ConfigMap labelled `grafana_dashboard` in
the `monitoring` namespace, which Grafana's sidecar loads into the
`local-airgap-llm` folder.

| Row | Panels |
|---|---|
| Status | Ready replicas, requests processing, requests deferred, generation speed, prompt speed, memory working set |
| Throughput | Tokens per second while busy (prompt, generation: the speed a request sees); tokens served per wall-clock second |
| Load | Requests processing and deferred over time (the scaling signal); busy slots per decode |
| Resources | Memory (working set, RSS, request, limit); CPU used vs request |
| Lifecycle | Desired vs ready replicas (the gap is the cold start); restarts and OOM kills |

Memory reads near the 6 GiB limit after a long prompt: the working set
includes about 1.3 GiB of reclaimable page cache from reading the model
file. The process itself (RSS) peaks at about 4.7 GiB at 32k context
([resource-plan.md](resource-plan.md)).

## Logs

Alloy (platform-lab) collects every pod's logs through the Kubernetes API
and ships them to Loki, so llama-server's and the KEDA components' logs
are in Loki with no change here (`{namespace="llm"}`, `{namespace="keda"}`).

**No prompt or response content is logged (decision, 11/22).** At its
default verbosity llama-server logs, per request, the slot, task id, token
counts and timings, never the text. Checked on the build cluster: none of
the test prompts or answers of the Week 3-4 tests appear in Loki. The
interceptor logs no request bodies either. So:

- llama-server runs at the default verbosity. `-v`/`--verbose`,
  `--log-verbosity` (or `LLAMA_ARG_LOG_VERBOSITY`) above the default and
  `--log-prompts-dir` (writes prompts to files) can expose prompts and
  outputs: use them only by hand on a test cluster, never in `deploy/`.
- Prompts can contain whatever a client sends (Phase 3 agents will send
  documents and tool output); keeping them out of a 7-day log store avoids
  a second copy of that data. If request tracing is needed later, it
  belongs in the client or an opt-in tracing layer, not in server logs.

Known platform issue (platform-lab, open): since 11/18 the node runs out of
inotify instances, and the kubelet writes `failed to create fsnotify
watcher: too many open files` into followed log streams, about 1,000-1,600
lines an hour across all namespaces. Logs still arrive; the fix is a
sysctl in platform-lab's base role.
